# RMC 完全分析ロジック（唯一の正本）

このファイルを RMC の定時更新ロジックの正本とする。定時実行側・ChatGPT 側・手動再実行側は、毎回このファイルを読み、ここに書かれた条件で分析する。別の古いプロンプトや旧ロジックを優先しない。

## 1. 実行時刻

- 日本時間 06:00
- 日本時間 17:00
- 日本時間 22:00

事前取得は原則として各本番時刻の約30〜40分前に行う。RMC の正式 run_id は `rmc-YYYYMMDD-0600` / `rmc-YYYYMMDD-1700` / `rmc-YYYYMMDD-2200` のみ。

## 2. 探索母集団

BET CHANNEL、カジ旅、遊雅堂、bet365 の取扱競技・市場の和集合を母集団にする。

- リアルスポーツ全競技
- eスポーツ全タイトル
- 一部競技に偏らせない
- 4サイトで同一イベントが重複する場合は同一試合として正規化する
- 取得不能サイト・取得不能市場は「取得不能」と明示し、推測で補完しない
- 4サイトの完全性を証明できない場合は `41/41 PASS` を偽装しない

各競技・各eスポーツタイトルについて、格差候補を最大 Top10 まで抽出する。10件未満なら実在する候補だけを扱い、数合わせをしない。

## 3. 格差一次スクリーニング

低オッズだけで格差と判定しない。競技別に、利用可能な次の情報を複数組み合わせて一次判定する。

- 世界ランキング、国内順位、Elo/Rating、シード
- 直近6〜10試合の勝率差
- 得失点差、セット差、ゲーム差、マップ差、ラウンド差
- 連勝/連敗
- H2H
- ホーム/アウェイ
- 相手レベル
- メンバー差、欠場、ローテーション
- 休養日、連戦、移動
- 市場オッズ差
- 競技固有の格差指標

一次候補はオッズ無しでも発見できること。市場は「実力格差」と「価格価値」を分けるために使う。

## 4. 完全 deep dive 必須項目

deep dive 対象は、可能な限り以下を全部調査して記録する。

1. 競技名
2. 国/地域
3. 正式大会名・リーグ名
4. ラウンド/節
5. 開催日
6. 日本時間開始時刻
7. 対戦カード
8. ホーム/アウェイ・会場
9. ランキング/順位/Rating と差
10. H2H（確認できる限り全件）
11. 直近6〜10試合の勝敗・スコア
12. 平均得失点、セット差、ゲーム差、マップ差、ラウンド差
13. 直近の共通対戦相手比較
14. 当日メンバー、先発、欠場、ローテーション
15. 休養日、連戦、移動距離
16. 前半/1stセット/1stゴール/序盤傾向（該当競技）
17. 最新オッズ
18. 必要勝率
19. 推定勝率
20. EV
21. 実力格差判定
22. 価格評価
23. 主なリスク
24. 取得できなかった情報

取れない項目は削除せず「未確認」「取得不能」として残す。

## 5. 共通相手比較

両者の直近6〜10試合を基準に、共通して対戦した相手を抽出する。共通相手があれば必ず以下を比較する。

- 勝敗
- スコア
- 得失点差
- セット/ゲーム/マップ/ラウンド差
- ホーム/アウェイ等の開催条件
- 対戦時期

同じ相手に対する成績差を、直接の勝率推定とは分けて説明する。共通相手が0件の場合は「共通相手なし」と明記する。

## 6. 序盤分析

競技に応じて序盤の格差を必ず見る。

- サッカー：前半、前半得失点、前半リード率、1st goal
- ハンドボール：前半30分
- バスケットボール：1Q / 前半
- バレー：1st set
- テニス：1st set
- 野球：序盤イニング傾向（取得可能な場合）
- アイスホッケー：1P
- eスポーツ：Map1 / early game / pistol / first objective 等、タイトルに適した指標

フルタイムの格差と序盤市場の格差は別評価する。

## 7. eスポーツ必須項目

- 大会・リーグ正式名
- BO形式
- 現在ロスター
- roster変更時期
- patch/version
- LAN / online
- H2H
- 直近シリーズ・マップ成績
- Map pool / map勝率
- Veto（確認可能なタイトル）
- 共通相手比較
- Tier差
- 最新市場価格

CS2、VALORANT、Dota 2、LoL、Rainbow Six、Mobile Legends、Rocket League、StarCraft、EA FC、NBA2K 等を一部だけに限定しない。

## 8. 4系統

RMC の以下4系統は独立探索・独立判定を維持する。

1. 推奨取引
2. VALUE①
3. VALUE②
4. PRO EDGE

共通候補リストを単純に振り分けない。同じ試合が複数系統に入っても、それぞれ独立して採否を決める。

## 9. 市場評価

各候補は次を分けて表示する。

- 実力格差が大きいか
- 現オッズで価値があるか

必要勝率は `1 / decimal odds` を基準とする。推定勝率との差から EV を算出する。1.01〜1.10 等の極端な低オッズは、実力格差が大きくても必要勝率が高すぎる場合があるため、価格評価を落とす。

## 10. 結果更新と収支

毎回、新規探索より先に既存カードの結果を確認する。

- ①〜④＋経験値取引の全カード
- 試合結果
- exact odds
- stake
- 払戻し
- 純損益
- ROI
- pending
- 複利
- 1/4 Kelly
- PRO EDGE の CLV

確定結果は公式または専門DBを優先し、結果ソースを記録する。敗戦は post-match review を追加し、「なぜ負けたか」を具体的に書く。

## 11. 公開ルール

- HTML/JSへカードや数値を直書きしない
- data JSON を本番パイプライン経由で更新する
- schema、重複、JST、locked、profit、CLV、future-info 等の全検証を通す
- main 反映後、Pages の公開データを再確認する
- 全工程成功時だけその run を「完全更新成功」とする
- inventoryだけ、rehearsalだけ、途中失敗runを「最新完全更新」と表示しない
- 失敗時は前回の公開成功runを維持する

## 12. 禁止事項

- 架空試合
- 架空オッズ
- 架空H2H
- 取得不能値の推測補完
- 低オッズのみでの格差判定
- 一部競技だけを見て「全競技確認済み」とすること
- 未完了をPASS扱いすること
- rehearsal/diagnostic payloadを本番候補として公開すること

## 13. データ不足の乱発防止

`insufficient_data` は通常の結論として大量に出してはいけない。deep dive に上げた試合は、まず外部公開情報を追加検索して実データを埋める。

- H2H、直近成績、ランキング/Rating、欠場/roster、競技固有情報について、少なくとも複数の検索経路を試す
- 公式、大会/リーグ公式、専門DB、信頼できる統計サイトを優先する
- 1つの検索で見つからないだけで「データ不足」にしない
- CI、rehearsal、dry-run、gate validation のダミー不足情報を本番候補として公開しない
- 本当に取得不能な候補は「追加調査が必要」へ分離し、採用候補・監視・除外の主一覧を埋め尽くさない
- 1系統でdeep diveが5件以上あり、その60%超が `insufficient_data` なら本番品質不足として公開を止め、前回成功runを維持する
- 本番 `system-analysis.json` には診断runを履歴として残さない
